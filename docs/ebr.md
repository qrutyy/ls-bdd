# EBR-таблица: `ht=ebr` и `ht=ebr+`

Индекс `lsv_ht` (сборка `TY=lf`, `DS=ht`) существует в трёх вариантах. Все они
реализуют один интерфейс (`src/utils/lock-free/ht_dta/ht_dta.h`, выбор — `ht=` в `src/Kbuild`):

| `ht=` | Схема освобождения памяти | Где код |
|---|---|---|
| `dta` (по умолчанию) | Drop the Anchor (Braginsky, Kogan, Petrank, SPAA'13) | `ht_dta/` |
| `ebr` | EBR Фрейзера, списки ожидания (limbo) у **каждого участника** | `ht_ebr/ebr.c` + `ht_ebr/ebr_local.c` |
| `ebr+` | EBR Фрейзера, **три общих** списка ожидания на таблицу | `ht_ebr/ebr.c` + `ht_ebr+/ebr_global.c` |

```sh
make init TY=lf DS=ht ht=ebr  ...   # или ht=ebr+
make kunit TY=lf ht=ebr+            # KUnit-наборы этого варианта
```

Источник: K. Fraser, *Practical lock-freedom*, PhD thesis, Cambridge, 2004,
UCAM-CL-TR-579, §5.2.3 (дальше [EBR]).

## 1. Что общее

`ebr` и `ebr+` отличаются только тем, где лежат удалённые ячейки и кто их
освобождает. Остальное общее:

- **Таблица** (`ht_ebr.c`): бакеты — сортированные списки Harris (бит удаления
  `0x1` в `next`). Ячейку отцепляет тот, чей CAS победил, и он же передаёт её
  в EBR (`ebr_retire_span`).
- **Эпоха и записи участников** (`ebr.c`). Глобальная `epoch` и по одной записи
  `state = (observed_epoch << 1) | ACTIVE` на участника, каждая в своей
  кэш-линии.
- **Вход** (`ebr_enter`): записать состояние, `smp_mb()`, перечитать эпоху;
  если она сдвинулась, объявить заново (не более двух раундов).
- **Выход** (`ebr_exit`): `smp_store_release(state, 0)`.
- **Сканирование** (`ebr_all_observed`): прочитать эпоху `e`, `smp_mb()`,
  пройти по всем записям. Эпоха может сдвинуться, если каждый активный
  участник видел `e`. Неактивные не мешают (сноска 1 в §5.2.3).
- **Частота попыток сдвига** одинаковая в обоих бэкендах. Попытка делается в
  конце операции, вне критической секции, если выполнено одно из условий:
  - каждая 32-я операция участника (`LSV_EBR_ADVANCE_FREQ`);
  - участник удалил ≥ 64 ячейки (`LSV_EBR_RETIRE_THRESHOLD`);
  - таблица заполнена на ≥ 80 % и у участника есть мусор;
  - операции не досталось ячейки.

  Попытка — это до двух сдвигов подряд.
- **Участники** — воркеры `lsv_wq`; id участника равен id воркера. Набор
  участников фиксируется при создании таблицы (`lsv_worker_id_limit()`).
- **Когда ячейку можно освободить.** В обоих бэкендах ячейка, удалённая в
  эпохе `r`, освобождается, когда глобальная эпоха дошла до `r + 2`, то есть
  после **двух** сдвигов.

## 2. Чем отличаются

| | `ebr` (у каждого участника) | `ebr+` (общие) |
|---|---|---|
| Где лежат удалённые ячейки | `limbo[3]` в личной записи участника | `list[3]` в состоянии таблицы |
| Добавление в список | обычные записи, без атомиков | один `try_cmpxchg` на голову общего списка за весь отцепленный участок |
| Конкуренция при удалениях | нет | все удаляющие участники бьют в голову одного из трёх списков |
| Кто освобождает | только владелец, свой мусор | тот, кто сдвинул эпоху, мусор **всех** |
| Сдвиг эпохи | сканирование + `cmpxchg(epoch)` | сканирование + захват `advancing` + проверка эпохи + `xchg(list)` + запись эпохи |
| Стоимость освобождения для одной операции | пропорциональна своему мусору | пропорциональна мусору всех участников за эпоху |
| Где вызывается `node_dealloc` | на воркере владельца (обычно тот же CPU) | на воркере того, кто сдвинул эпоху |
| Мусор участника, который перестал работать с таблицей | висит до запроса на освобождение или до `lsv_ht_free` | освобождают чужие сдвиги |
| Операции не хватило ячейки (`no_cell`) | освобождает своё и ставит **запросы на освобождение** на воркеры остальных; ячейка вернётся *следующей* вставке | два сдвига освобождают общий мусор; вставка повторяется **сразу** |
| Задания на чужих воркерах | есть (`reclaim_ctx`, `reclaim_pending`) | нет |
| `lsv_ht_free` | ждёт запросы, поставленные на других воркерах; запрос на своём воркере освобождает остаток памяти сам | ничего не ждёт |
| Состояние на участника | 3 списка + счётчики + `lsv_wq_ctx` | два счётчика |
| Блокировка | нет | trylock на сдвиг эпохи (`advancing`); тот, кто удаляет или читает, его не ждёт |

Что из этого следует:

- **`ebr`** дешевле на пути удаления: нет общих записей. Он хорошо
  масштабируется при интенсивной записи, и свой мусор освобождает тот же CPU.
  Минус в том, что чужой мусор нельзя освободить. Поэтому нужен механизм
  запросов к воркеру-владельцу, а с ним приходят ожидание в `lsv_ht_free` и
  его тонкие места: гонка с `lsv_wq_destroy`, ожидание без ограничения по
  времени.
- **`ebr+`** проще по жизненному циклу: нет заданий, нет ожиданий, мусор
  неактивных участников не залёживается, а нехватка ячеек решается прямо в
  операции. Цена:
  - общая голова списка, по которой бьют на каждом удалении;
  - неравномерная задержка: один участник освобождает мусор всех;
  - сдвиги эпохи выполняются по одному (claim).

Это гипотезы по устройству кода, производительность не измерялась. Сравнить
можно через `lsv-bench`, собрав модуль с `ht=ebr` и с `ht=ebr+`.

## 3. Отступления от [EBR]

### 3.1. Общие для обоих бэкендов

1. **Эпоха удаления берётся после отцепления, а не при входе.**
   - В [EBR] ячейка идёт в список эпохи, которую удаляющий *наблюдал в начале
     операции*. Такой участник может дописывать в список `e − 1`, когда
     остальные уже в `e`. Поэтому при сдвиге `e → e + 1` безопасно освободить
     только список `e − 2`, и ячейка ждёт **три** сдвига («the limbo list that
     was populated two epochs ago»).
   - У нас эпоха читается заново сразу после отцепляющего CAS (CAS — полный
     барьер). Ячейка из списка `r` была отцеплена *до* того, как эпоха стала
     `r + 1`. Читатель, вошедший в `r + 1` или позже, до неё не дотянется.
     Поэтому достаточно эпохи `r + 2`, то есть двух сдвигов.
   - По модели памяти ядра (LKMM) это цикл
     `W(отцепление) ; mb ; R(epoch)=r ->fr W(epoch)=r+1 ->rf R(epoch)=r+1 ; mb ; R(ссылка)`.
     Отношение `pb` в нём циклично, поэтому такое исполнение запрещено.
     Litmus-тест для herd7 пока не написан, это нужно доделать.
2. **Когда пытаться сдвинуть эпоху.** В [EBR] — «вероятностно» при *входе* в
   секцию. У нас — детерминированно раз в 32 операции и досрочно (см. §1), в
   конце операции, вне секции. Сканирующий участник в этот момент в покое и
   сам себе не мешает. Поэтому он может сдвинуть эпоху два раза подряд, и его
   собственный свежий мусор созревает без участия других.
3. **Повторное объявление при входе.** Если эпоха сдвинулась между записью
   состояния и барьером, участник объявляется заново. Безопасно было бы и без
   этого: устаревшее объявление только задерживает сдвиг.
4. **Освобождение.** У Фрейзера в [EBR] есть свой free list. У нас ячейки
   возвращаются через `ops->node_dealloc` (по одному вызову на ячейку): так
   владелец ячеек, например `ds_control`, может вести учёт.
5. **Участники.** В [EBR] — процессы из списка процессов. У нас — воркеры
   `lsv_wq` с фиксированным набором id на момент создания таблицы. Воркер,
   созданный позже, получает отказ во всех операциях.
6. **Лишняя эпоха для Alpha** (§5.3: инициализация освобождённых объектов
   нулями) не нужна. Порядок зависимых чтений обеспечивают
   `READ_ONCE`/LKMM.

### 3.2. Только `ebr`

7. **Списки у каждого участника.** Текст §5.2.3 описывает общие списки (это
   `ebr+`). Списки у каждого потока — частая схема в реализациях EBR
   (например, crossbeam-epoch, DEBRA). Как устроена собственная библиотека
   Фрейзера, я по исходникам **не проверял**.
8. **Немедленное освобождение списка с тем же остатком `e mod 3`.** Если в
   ячейке списка лежит мусор другой эпохи с тем же остатком, он отстаёт
   минимум на 3 эпохи, и его освобождают сразу (с `smp_mb()` перед этим).
9. **Запросы на освобождение.** Это механизм, которого нет в [EBR] и который
   нужен только из-за личных списков. Он используется, когда вставке не
   хватило ячейки.

### 3.3. Только `ebr+`

10. **Сдвиги эпохи по одному (claim).** Текст не описывает, что делать, если
    сдвигают двое одновременно. Если реализовать «в лоб» (просканировал —
    отцепил старейший список — сдвинул эпоху), получается use-after-free:
    1. участник A просканировал эпоху `E` и задержался;
    2. остальные довели эпоху до `X ≡ E + 2 (mod 3)` и удалили ячейки в `X`,
       а читатель стоит на одной из них;
    3. A отцепляет «старейший» для `E` список `(E − 1) mod 3`, но это теперь
       список `X`, и A освобождает ячейку под читателем.

    Поэтому сдвиг захватывается флагом `advancing`. После захвата проверяется,
    что эпоха всё ещё `E`, и только потом список отцепляется и эпоха
    публикуется. Этот сценарий проверяет KUnit-тест `ebr_stale_advancer`.
11. **`preempt_disable()` на окне захвата** (две записи): вытесненный
    сдвигающий не задерживает остальных.
12. **Какой список освобождать.** Из п. 1 следует, что при сдвиге `e → e + 1`
    освобождается список `e − 1`, а не `e − 2`, как в тексте. Отцепление идёт
    до публикации `e + 1`, а `atomic64_read_acquire` при удалении парен
    этой публикации. В таком режиме хватило бы двух списков; оставлено три,
    как в тексте.
13. **Отцепленный участок добавляется одним CAS.** Участок связывается в
    цепочку по `removed_link` и добавляется в общий список одним
    `try_cmpxchg`. ABA здесь невозможна: список, в который пишет участник,
    отцепляется только при сдвиге `e + 1 → e + 2`, а этот участник в своей
    секции держит эпоху не дальше `e + 1`.

## 4. Почему это безопасно (кратко)

- **Инвариант.** Ячейку из списка эпохи `r` освобождают только после того,
  как кто-то, прочитав эпоху `≥ r + 2`, выполнил полный барьер: `smp_mb()` в
  `ebr_reclaim` / `ebr_retire` (`ebr`) или успешный `atomic_cmpxchg` захвата
  (`ebr+`).
- Сдвиг на `r + 2` означает, что в момент сканирования для `r + 1 → r + 2` ни
  один участник с эпохой `≤ r` не был в секции (`smp_mb` в `ebr_enter` и
  `ebr_all_observed` образуют пару store-buffering).
- По п. 1 ни одна секция с эпохой `≥ r + 1` не могла дотянуться до ячейки.
- Последние чтения ячейки из завершённой секции упорядочены перед её
  `smp_store_release(state, 0)`, а освобождение идёт после барьера, который
  следует за чтением этого состояния.

Проверка формальными средствами (herd7, GenMC) не делалась, см. §6.

## 5. Тесты

| Набор | Где | На чём запускается | Что проверяет |
|---|---|---|---|
| `lsv_ht_<impl>` | `utils/lock-free/ht_tests/suites/kunit_lsv_ht_*.c` | `dta`, `ebr`, `ebr+` | контракт интерфейса: вставка/поиск/удаление, зарезервированные ключи, ёмкость, мёртвые значения не выдаются, поздний `remove` не трогает новое значение, режим без счётчика ссылок, `insert_node`, отказ позднему воркеру, исчерпание пула и возврат ячеек, `lsv_ht_free` с элементами, конкурентная нагрузка (в том числе с переиспользованием адресов ячеек — ABA). Во всех тестах проверяется: ни один обход не наступил на освобождённую ячейку, каждая ячейка возвращена ровно один раз, живое значение не потеряло последнюю ячейку, на ключ не больше одного живого значения. |
| `lsv_ht_ebr_local` / `lsv_ht_ebr_global` | `ht_ebr/tests/suites/kunit_lsv_ebr_reg.c` | `ebr` / `ebr+` | одиночный участник освобождает всё; остановившийся читатель держит эпоху (не дальше `+1`, ничего не освобождено); **разное поведение**: мусор неактивного участника (`ebr`: лежит, `ebr+`: освобождён чужими сдвигами); нехватка ячеек (`ebr`: отказ + запрос + успех следующей вставки, `ebr+`: успех сразу); устаревший сдвигающий (п. 10); стресс-тест |
| DtA-наборы | `ht_dta/tests/` | `dta` | без изменений |

Карантин освобождённых ячеек в тестах ограничен 64K ячейками, после этого они
освобождаются по-настоящему. Use-after-free за этой границей должен ловить
KASAN.

## 6. Что не сделано и известные ограничения

- Сборка без предупреждений (`-Wall -Wextra`, `W=1`) для `dta`, `ebr`, `ebr+`:
  Fedora 7.2.10 x86_64 и Fedora 7.2.9 aarch64.
- KUnit на 7.2.9 aarch64 (4 vCPU, `CONFIG_PREEMPT`, без KASAN): `ebr` и `ebr+`
  проходят 5 прогонов из 5 (`lsv_ht_ebr_*` 7/7, `lsv_ht_<impl>` 12/12);
  `dta` проходит `lsv_ht_<impl>` 12/12.
- Мутационная проверка: если в `ebr+` убрать перепроверку эпохи после захвата,
  `ebr_stale_advancer` падает (ячейка под читателем освобождена).
- Пять существующих DtA-тестов (`ht_concurrent_participants*`,
  `ht_concurrent_recovery*`) падают в этой ВМ точно так же и на `main`: им
  нужно больше 4 CPU.
- KASAN, lockdep и kmemleak не включались.
- Нет litmus-тестов LKMM для п. 1 и для пары вход/сканирование, нет проверки
  через GenMC.
- В обоих бэкендах объём освобождения за одну операцию не ограничен. В `ebr+`
  это хуже: участник, сдвинувший эпоху, освобождает мусор всех.
- Остановившийся (вытесненный или спящий) участник блокирует освобождение в
  обоих бэкендах; это свойство EBR как такового.
- Сканирование стоит O(`nr_threads`), а `nr_threads` — все id воркеров, когда-либо
  созданных в модуле.
- Таблица работает только на воркерах `lsv_wq`, а в production-пути их пока
  нет (см. требования к архитектуре).
